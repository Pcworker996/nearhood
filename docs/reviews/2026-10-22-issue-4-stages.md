# Ticket #4 staged workflow — verification record

October 22, 2026. Scope: [#4](../issues/4.md), [ADR 0005](../adr/0005-separate-extraction-from-matching.md), and [implementation contract](../implementation/report-processing-stages.md). This records local implementation, not a claim of deployment or ticket completion.

## Implemented

Dedicated extraction and matching calls run as separate resumable requests with a private versioned checkpoint. Software validates source passage IDs and stores exact original supports beside full Report context. Candidate comparison considers up to 20 Happenings, records omitted coverage, limits total input, and selects at most five review cards. Existing membership requires an attributed contributor decision. Multiple situations remain saved/unassigned with an explanation. Stale snapshots, stage failures and incomplete no-match evidence cannot publish.

Review found an untracked evidence cap and a publication race. A regression reproduced two simultaneous empty searches creating two Happenings; transaction-scoped serialization plus retrieval under the lock fixes it. Evidence omission counts now reach both comparison and publication validation. Localized source support replaces the whole-Report-only reference while retaining complete original context. This source check validates references; it does not prove that an interpretation follows from the text.

## Comparable recorded outcomes

[Recorded synthetic model results](artifacts/2026-10-22-issue-4-models.json) retain original scenario text, expected/actual outcomes, extraction source support, errors, latency and available usage. Reproduce with `npm run model:check`, then `npm run model:check -- --baseline`; add `--held-out` for the four frozen held-out cases. These held-out examples have now been inspected; future prompt tuning needs a new holdout set.

| Set                        | Staged v5/v3          | Combined baseline | Staged total latency | Baseline total latency |
| -------------------------- | --------------------- | ----------------- | -------------------- | ---------------------- |
| Development, 8 examples    | 6/8 expected outcomes | 3/8               | 876–2,317 ms         | 2,966–8,112 ms         |
| Fresh held-out, 4 examples | 3/4 expected outcomes | 2/4               | 1,467–2,270 ms       | 4,735–7,326 ms         |

The baseline had validation failures and one overly confident match where continuity was unknown. Staged calls had zero stage/validation failures in the final twelve examples but three unnecessary uncertainties. Baseline and stages differ in schema, prompting, output budget and thinking configuration, so the comparison cannot attribute improvements to two calls alone. Original identity evidence and scope are supplied in these small fixtures; they do not measure open-world retrieval recall. The beyond-five API regression verifies one appropriate sixth candidate reaches comparison. Larger-pool and packet-size defaults remain evaluated starting limits, not a demonstrated optimal threshold.

Final stages maxed at 1,390 ms per provider call, within the 25-second provider / 60-second route and lease limits; fixtures also cover slow calls and concurrent attempts. Development stages used 13,169 prompt / 2,123 completion tokens in total; held-out stages used 7,394 / 1,153. Baseline usage was not instrumented, so no token-cost superiority is claimed. These observed timings do not guarantee hosted latency. Database statements and connection acquisition have 5-second limits, idle transactions 10 seconds. A provider deadline leaves route margin for auth, checkpoint/query work and short publication; publication failure clears its provisional create-new decision so the saved Report cannot appear as a pending no-match pin. New concurrency assertions reproduced that old projection (HTTP 200) and now verify HTTP 404 for the unassigned loser.
