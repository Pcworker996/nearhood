# Ticket #4 processing contract — version 2

Implementation contract, October 22, 2026. Source: [ticket #4](https://github.com/Pcworker996/nebius-hack/issues/4), [accepted strategy](../proposals/report-matching-strategy.md), and [ADR 0005](../adr/0005-separate-extraction-from-matching.md). These are chosen implementation limits to evaluate, not measured accuracy or hosting guarantees.

- `report-extraction-v5`: strict provider JSON `{category, observations}`. Category is disruption/safety/activity. Each Observation supplies an occurrenceGroup integer (0–11) or null. Software derives single when all groups agree, multiple for distinct groups, unclear if any group is null. Distinct scopes, changes, disagreements and unknown history do not by themselves make separate groups. Each of 1–12 Observations has a unique local key (40 characters), subject (80), sourceRef (the fixed submitted_report reference), 1–12 unique sourceIds selected from software-numbered sentence passages, occurrenceGroup, nullable describedCondition (160), nullable exact spatialScope (80), nullable exact timeWording (160), and nullable uncertainty (240). Software validates each sourceId against the submitted Report and stores the exact original text and UTF-16 start/end offsets in the extraction and published Observation.sourceSupport. Supporting passages can be expanded in the evidence card. The complete Report is retained alongside these passages so segmentation cannot erase qualifications. Models must ground derived labels in the cited passages; structural validation establishes an existing source, not semantic entailment or truth. Derived subject/condition labels remain interpretations; full original text is the stored evidence context and initial claim. Unknowns stay null; model wording never replaces explicit form time/coordinates. The request contains no candidates.
- `report-matching-v3`: strict JSON `{assessments}` with one assessment per supplied candidate (maximum 20). Each has candidateId, continuity (same/separate/unknown), chronology (consistent/change/conflict/unknown), scope (same/overlapping/different/unknown), 1–3 candidate-specific Observation evidenceIds and a reason (320 characters). The provider schema restricts IDs to the supplied candidate/Observation enums; software additionally checks candidate-specific ownership, uniqueness and complete assessment coverage. Output order ranks candidates; software derives match/no-match/uncertainty and the five-card review set. Conflict is not a veto on identity. Unknown continuity or incomplete evidence prevents automatic creation. A unique supported same-occurrence assessment can still be shown for confirmation when evidence is omitted; it cannot justify create-new.
- Provider budgets: 25 seconds per stage, extraction output 8,192 tokens, comparison output 8,192 tokens. Nemotron 3 calls disable thinking via chat_template_kwargs.enable_thinking=false; other models retain provider defaults. Matching serialized user input is capped at 65,536 UTF-8 bytes; duplicate original Reports are sent once. Oversized packets remain saved/unassigned with an explanation, not silently truncated into no-match. Spatial/time defaults remain 1,500 m / symmetric 30 days with unknown-time eligibility. Retrieve 21 rows to detect overflow beyond the 20-candidate cap; record coverage. Select an original identity Observation plus relevant later evidence, preferring different Reports before additional Observations of one Report, at most three per candidate. Coverage records the overflow candidate ID and the number of omitted Observations per candidate (the candidate overflow count is a lower bound, not an exhaustive total). Counts and the full selected packet enter the fingerprint and comparison input. Any omitted Observation conservatively blocks create-new, even if its original Report is also represented.
- Private checkpoint: extraction JSON, input fingerprint, extraction version/model, per-stage latency/usage, current processing stage (extraction/matching), pending reason, matching schema version, full assessed candidate snapshot, snapshot fingerprint and assessments. Existing original Reports, memberships and published accounts survive migration. Existing unpublished old-schema reviews must be reprocessed before confirmation; no automatic provider backfill.
- Recovery API adds processingStage, extractionReady, nextAction (process/retry/review/wait/none), and pendingReason to the owner's saved Report. It does not expose raw provider responses or credentials. `POST .../process` claims one stage per request. After extraction it returns saved/matching/process; the client advances the next POST. Matching errors return pending/matching/retry while retaining compatible extraction. Multiple/unclear occurrences stop unassigned with a reason. GET never advances processing.
- Each stage uses a 60-second lease with an attempt token, checkpoint writes require the unexpired owned attempt, and no provider work happens in a database transaction. Match decisions revalidate the candidate snapshot, checkpoint version and actual shown/review set. An unshown plausible candidate or incomplete packet blocks create-new. Publication is short, atomic and idempotent. All application publication paths acquire one transaction-scoped advisory lock, then repeat retrieval on that transaction before checking the snapshot. This deliberately serializes publication for the small hackathon workload and covers initially empty candidate pools. Provider calls run before the lock. Other database writers would need to honor this boundary too; it is not a general-purpose multi-service locking protocol.
- Evaluation gates before a live-ready claim: all deterministic contract/product regressions pass; zero wrong merges or unsupported no-match creation in the reviewed release scenarios; expected supported cases retain scope/qualifications and require confirmation; every stage fits its configured deadline. Report exact scenario counts, held-out outcomes, uncertainty, candidate recall, total latency and token usage without claiming general accuracy from a small set. Compare against the preserved earlier combined-call strategy; separate provider quality from controlled-service checks. The 20-candidate/input/time limits may change only with documented results and matching version changes where semantics change.
