# #20: Pending Reports stall until their contributor retries, and can become unreachable

**State at export:** open · **Labels:** needs-triage · **Opened:** 2026-10-28

_Exported from the private project tracker on 2026-10-30._

---

Recording observed behavior only. No fix or plan is proposed here.

## What happens

A Report that becomes `pending` only moves forward when its contributor's browser calls `POST /api/reports/[id]/process`.

- A failed or interrupted processing attempt leaves the Report `pending` (`extraction_failed`, `matching_failed`, `*_interrupted`). See the catch block in `src/lib/report-processing.ts` and the lease-expiry projection in `savedSelect` (`src/lib/report-submission.ts`).
- `savedReport()` maps `pending` to `nextAction: "retry"`. The client auto-processes only when `nextAction === "process"`, so a pending Report waits for the "Retry account update" button (`src/components/contribution.tsx`).
- No server-side retry exists: no cron job, queue or worker. Only the owning contributor can call the process route.

## Contributors can lose the way back

- The only handle to a saved Report is `/?contribute=1&report=<id>`. The draft and request key are deleted from localStorage once the save succeeds.
- No endpoint or view lists a contributor's Reports.
- A contributor who closes the tab without the URL can't reach the Report again.

## What stays in the database

- `nearhood.reports` and `nearhood.report_processing` (`state='pending'`, plus any checkpoint reached so far) remain.
- No Observations, memberships, Happening or Shared Account version exist for it, because publication is a single transaction.
- No cleanup touches these rows. The only deletes are in `scripts/report-lease.test.ts`.
- Nothing counts or logs stranded Reports, so how often this happens isn't visible.

## Pending marker looks unreachable (not yet verified)

`pendingReports()` in `src/lib/database.ts` shows a public "Pending Report" marker only when `state='pending' AND matching_outcome='create_new'`. As far as I can tell, no current code path produces that combination:

- The failure handler sets `matching_outcome=NULL` when it moves a Report to `pending`.
- An interrupted publish leaves the stored state as `processing`. The `pending` value only appears in the read projection.

If this is right, the marker and the "Inspect public evidence" link for pending Reports in `contribution.tsx` never appear. This hasn't been confirmed against a live database.

## Two kinds of waiting

Some states wait on a contributor's decision (`match_review`, `clarification`, per ADR 0004). Others wait only because a mechanical failure needs another run. Today both depend on the contributor coming back.

## Open questions (undecided)

- Should mechanical failures progress without the contributor?
- What should happen to a Report that stays in `match_review` or `clarification` indefinitely?
- Should unpublished Reports appear on the public map at all?
