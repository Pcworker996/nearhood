## Comment from 2026-10-27

**Category is set once at creation (from #4 test planning)**

In #4, a Happening's category comes from the first Report's extraction and never changes. Reports confirmed into it later still get a category from extraction, but it's saved only in their private processing record. Example: "police tape, not sure why" (`disruption`) followed by "gas leak, playground evacuated" (`safety`) leaves the Happening as `disruption`.

During reconciliation, reconsider the category using all member evidence, and record any change in account history so it can be inspected. One possible interim rule is that a category can go up but never down (`safety` > `disruption` > `activity`), because over-warning costs less than hiding a hazard.

The #4 test CA-06 keeps today's fixed-category behavior on purpose, so expect to update it when this changes. See `docs/proposals/ticket-4-test-plan.md` (Q1).

## Comment from 2026-10-27

**Contributor category correction: deferred here (from #4 test planning)**

#4 doesn't let contributors correct a Happening's category. The model can't tell a malicious correction from a genuine one, because intent isn't in the Report text. Options for when this is picked up with category reconsideration:
- **Correction as evidence:** a suggested category is attributed and shown ("1 contributor suggests: Safety concern") but doesn't overwrite the label.
- **Uneven rules:** raising to `safety` is easy; lowering a hazard to `activity` needs another contributor to agree.
- **Agreement across contributors** during reconciliation.

For #4, the extraction prompt (v7) defines the categories, and the live evaluation fails on any hazard labelled `activity`. See `docs/proposals/ticket-4-test-plan.md` (Q4).
