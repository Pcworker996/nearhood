## Problem Statement

People need to understand nearby conditions and find activities they can participate in, but individual observations are fragmented, become stale, and can disagree. A newer submission may describe an older observation; several contributors may repeat one source; a report of improvement may cover only part of the original problem. Readers need enough context to decide whether to change a route, attend an activity, or contribute information without mistaking popularity or an AI summary for verified truth.

The core user question is: **What does the available evidence currently support about this real-world local happening?** A collection of reports or a fluent AI paragraph alone does not answer it. Readers need to distinguish what changed over time, which parts of a place were observed, and which disagreements remain unresolved.

Contributors also need a simple way to share what they know without first deciding which category or existing happening their report belongs to. Their original accounts, including biased and conflicting accounts, must remain inspectable as the shared account evolves.

## Solution

**Nearhood turns fragmented local observations into evolving, evidence-linked happenings so people can understand what is currently known, what changed, and what remains uncertain.**

Build Version 1 as a mobile-friendly web app organized around Happenings. Anyone can browse and any signed-in person can submit a Report. The system interprets Reports into structured Observations, matches them to Happenings, reconciles their temporal and spatial relationships, assesses provisional state, and presents a grounded Shared account. Its Shared summary is a concise presentation of that account. Readers can inspect each important claim through its supporting Observations back to the original Reports. Activities use this same information model; stored-happening discovery, directions, calendar actions, and private updates support useful action on that understanding.

Use the supplied Nearhood Figma design for presentation, extending its visual language for the agreed behaviors. Deliver a real interactive map, persistent backend, sign-in, and runtime NVIDIA open-source model integration through Nebius Token Factory. Demonstrate the fictional Northbank scenarios over a downtown Detroit street basemap, clearly identifying the sample happenings as demo data.

## Implementation Decisions

### Foundational information model

- The core product object is an evolving real-world Happening, not a submitted Report, alert, ticket, or social post. Preserve the distinct chain **Report → Observation → Happening → Shared account**.
- A Report is an original attributed submission. An Observation is a structured interpretation of a claim from that submission, with subject, described state, observation time or unknown, relevant location/spatial scope, and a link to the precise source Report or report revision. A Report can yield several Observations. Extraction is derived interpretation, not independent verification.
- A Happening maintains an evolving Shared account of supported state, chronology, spatial scope, changes, disagreement, and uncertainty. The Shared summary is the concise readable presentation, not the entire stored account or a replacement for evidence.
- Activities, disruptions, and safety concerns are categories of the same Happening model, with category-specific scheduling or freshness behavior. Do not create a disconnected activities information model.
- Distinguish known/supported, unknown, conflicting, stale, and partially improved information in the account. These can coexist across scopes; do not compress them into a binary active/resolved value. Keep the agreed V1 user-facing status labels rather than introducing every illustrative lifecycle name from the guardrails.

### Delivery and application responsibilities

- Deliver a mobile-friendly web application backed by an API and persistent storage. The existing throwaway prototype has in-memory data, an illustrated map, and stubbed actions; it is visual-flow prior art, not an existing production backend.
- Application responsibilities comprise geographic browsing and highlights; report submission and preserved revisions; observation extraction, candidate retrieval and matching; evidence relationships and temporal/spatial reconciliation; happening details, claim-level evidence inspection, evidence timeline, and grounded Shared accounts; resolution assessment and freshness; stored-happening discovery; organizer schedule controls; private subscriptions and in-app notifications; and account authorization.
- Proceed with a fast, simple mobile-friendly web V1 using Next.js and TypeScript for the frontend and HTTP/JSON API, PostgreSQL with PostGIS (Supabase for hosted database), and Leaflet with MapTiler for the real street map.
- Use Supabase Auth with Google sign-in only for V1. Browsing remains public; contribution and private update preferences require sign-in. Preserve a contribution draft through sign-in. Keep email private and use a contributor-chosen public display name; backend authorization enforces ownership and private access.
- Use an eligible NVIDIA Nemotron model through backend runtime calls to Nebius Token Factory. The exact available model must pass a small structured-output/evidence/latency integration check before selection; a model identifier is not yet confirmed.
- Expose ordinary HTTP/JSON application contracts so a later SwiftUI client can share the backend. Native Apple delivery is later work.
- Keep background processing and retries durable; worker hosting, app hosting, and service credentials remain setup choices to resolve explicitly, not implicit selections.
- Browse publicly. Require sign-in for contributing and persistent account-specific choices. Enforce ownership for updates and matching corrections to a contributor's reports, designated organizer controls, and access to private choices and notifications through the backend.

### Map, highlights, and demo

- Use Leaflet for interactive pan, zoom, markers, and coordinate selection, with MapTiler's free plan supplying street-map tiles for the initial demo. Configure an account/API key and comply with provider branding, usage limits, and attribution. Use the real downtown Detroit basemap represented by the prototype's coordinates; clearly label the Northbank sample happenings as fictional demo data.
- Seed the Eastbank footbridge closure, streetlamp outage on Alder at 3rd, and Canal Green stretch-and-picnic activity. Final coordinates must support the demonstration in that area.
- Scope map markers, highlights, and their two sections to the visible map bounds. Resolve distance from shared reader location when available, otherwise map center, and label the reference point. Location sharing remains optional.
- Disruptions and safety: potential effect on plans first, then observation freshness and distance, with a concise reason for emphasis and uncertainty preserved. Activities: ongoing first, then upcoming by start time, distance breaking ties. Importance is distinct from evidential support.
- Empty map areas show No happenings here yet and Return to demo. Unknown, stale, and Reported resolved conditions remain accessible with appropriately quieter markers; Reported resolved leaves urgent highlights.

### Contribution interaction

- Use a form with natural-language Report text, explicit observation time or unknown, adjustable pin/location, firsthand/source-based provenance and an optional contributor-cited link. Do not require category or newness classification; preserve drafts through Google sign-in.
- Save the immutable original before provider work. A dedicated first LLM call extracts source-linked JSON; validate and checkpoint it separately. A second LLM call assesses candidate identity using that JSON, the original Report and inspectable candidate evidence. Invalid extraction never advances to matching.
- Deterministic software retrieves a larger bounded nearby pool before semantic comparison. Evaluate an initial cap of 20 with documented spatial/time constraints, then show the best suggestion and up to four alternatives. Do not discard all but five by time/distance before the semantic comparison. Exact caps and evidence budgets require evaluation.
- Require contributor confirmation before existing-Happening membership for both initial Reports and Add an update. A selected detail supplies search context, not membership. Show original evidence, chronology, location and a supported explanation; allow confirmation, rejection of displayed candidates, or explicit uncertainty.
- Create a Happening only after successful extraction/search and comparison support one coherent occurrence with no plausible existing match, including a successful empty search within the documented scope. Failed/incomplete search, inadequate evidence coverage, ambiguity or invalid output remains saved/unassigned or retryable, never a default new pin. Rejecting displayed candidates does not reject unshown plausible candidates.
- Conflicting accounts can describe the same Happening. Distinguish occurrence identity from agreement, temporal change and spatial scope. A later recurrence requires evidence of a distinct occurrence; elapsed time or Reported resolved alone is insufficient. Unclear continuity stays unassigned and prompts a focused question.
- For multiple separate occurrences, preserve the original Report and valid derived interpretation unassigned; explain that it describes separate situations. Guided answers and distribution are deferred beyond the hackathon. No partial attachment, duplicate Report or invented account is permitted.
- Keep original text and any supported clarification answers separate from derived interpretations, with attribution/time. Candidate choices remain the milestone's existing clarification mechanism; richer ordinary-language continuity answers and own-report rematching remain #6 work, and the multi-occurrence answer flow needs a later design.
- A full conversational contribution interface is not required. Processing phases and failures must be comprehensible without exposing internal schema or provider details in the form.

### Stored records and operations

- Persist contributors/accounts; original Reports and report revision/update histories; structured Observations with source-report/revision links, subjects, states, observation times and spatial scopes; Happenings and their observation membership/matching history; contributor-cited sources and known shared-source relationships; evidence relationships; versioned Shared accounts and their claim-level evidence references; Shared summaries; Resolution assessments and status history; activity schedules and explicit organizer designation; private Interested / Follow updates choices; and in-app notifications.
- Preserve a traceable claim → supporting Observation → original Report/revision path. Derived records must reference actual stored evidence. Record the basis of relevant account changes so readers can compare the previous understanding with the new evidence. This requires inspectable history, not a full event-sourcing architecture or unrestricted historical search.
- Represent evidence relationships needed for corroboration, contradiction, shared-source repetition, temporal transition, and different spatial scope. State which relationship is supported and retain ambiguity when it cannot be established. Do not claim independent evidence merely because contributor IDs differ.
- A Report carries contributor identity, written account, location, provenance, observation time or explicit unknown, submission time, optional cited source, and inspectable association to its derived Observations and their Happening. Preserve original accounts and update history; do not substitute generated text for original submissions.
- Separate New observation from Correction. Preserve the earlier account and its times. Report stack ordering is newest observation first with unknown times clearly labeled rather than made recent by submission time. Provide an evidence timeline that preserves observation chronology and distinguishes submission times, report corrections, and subsequent observations. A multi-observation Report must not make all its claims inherit the newest claim’s time or scope.
- Support API operations for visible-area browsing and detail, claim-level Observation/Report inspection and account/evidence history, contribution, own-report update and matching correction, candidate-match clarification, discovery and geographic expansion, organizer schedule/cancellation changes, private update choices, and own notifications. Exact endpoint naming and payload formats remain implementation planning work; keep these observable contracts consistent across client and backend.
- Group reports citing the same article under one source while keeping all contributors visible. Show distinct contributor participation separately from cited-source count. Same-source repetition is not independent corroboration; cross-source syndication detection is deferred.
- Keep biased accounts attributed in the Report stack. Bias alone does not hide, delete, or remove their contributions. Version 1 does not include the proposed flag-and-hide workflow.

### Processing, failure and publication

- If model processing fails, keep the saved original Report visible and show Report saved · account update pending. Do not present failed processing as a successful account update.
- Retain the previous published Shared account, when one exists, while the new update is pending. Distinguish the pending Report from the evidence already incorporated into that account. For a first Report, there is no previous account to manufacture; keep the Report inspectable without invented synthesis.
- Offer a retry of processing for the same saved Report without requiring resubmission or creating duplicate Reports.
- Acceptance example: submit an update, simulate model failure, reload and inspect the preserved Report and unchanged previous account, then retry successfully; incorporate the saved Report once and expose the resulting evidence-linked account change.

- Preserve durable processing and retries. An older processing result must not overwrite an account based on newer evidence, or reintroduce a corrected revision or obsolete membership. Account publication must remain grounded in the applicable evidence set; retries incorporate a saved Report once.
- If a successful matching pass finds no plausible existing Happening but later account processing fails, show a Report-only pending marker at the known location, labeled Report saved · account update pending; opening it exposes the Report without invented synthesis. A search/model failure before a no-match decision remains saved and retryable without a new pin. For ambiguous membership, keep the Report unassigned and show its pending state in the contribution flow.

### Reasoning workflow and deterministic boundaries

- Use one fixed software-controlled workflow: immutable saving → dedicated LLM extraction → validation and durable JSON checkpoint → deterministic candidate retrieval → separate LLM matching → contributor review → authorized publication. Models cannot choose tools, run an open-ended search loop or write memberships.
- Extraction describes claims, subject/target text, reported conditions, scope, time wording, provenance context and uncertainty, with references to source passages. Missing details stay unknown; preserve negation and qualifications. Explicit form timestamps/coordinates remain deterministic inputs and are not silently replaced by prose interpretation. A physical-target description is not a registry identity.
- Matching receives original evidence as well as JSON. Validate supplied candidate/evidence IDs and preserve assessments of occurrence continuity, chronology, scope and disagreement. Conflict is not a veto on same-occurrence membership; unknown attributes are not evidence of a separate occurrence.
- Retrieve a bounded larger nearby pool, initially evaluating 20, then select up to five review candidates by semantic assessment. Document geographic/time constraints, unknown-time behavior, candidate ordering and coverage; category is not a hard filter. Bound total input size, deduplicate repeated original Reports, preserve relevant source context and record omitted/truncated coverage. Inadequate coverage must yield uncertainty instead of unsupported no-match creation.
- Persist extraction and matching stages independently with input/schema/prompt/model versions, attempts/leases, candidate snapshots, assessed versus displayed IDs, attributed decisions and retry reasons. Reuse only compatible extraction; refresh candidate evidence for matching retry. Obsolete results cannot overwrite newer work.
- Execute at most one provider stage per processing request, with independently verified hosting and lease budgets. The existing 35-second call timeout cannot simply be doubled within a 60-second route. Keep provider work outside database transactions; perform short, version-checked membership/account transactions. Advance through authorized POSTs and expose recovery through owner-only read APIs.
- Account reconciliation, temporal reasoning, state assessment and grounded synthesis remain subsequent validated responsibilities in #5. Two calls describes extraction/matching, not a limit on every model operation in V1. Important claims must link through Observations to original Reports; a real citation must support the actual scope, not merely exist.
- Software owns timestamps, explicit time inputs, coordinates, distances, IDs, persistence, authorization, evidence links, account versions, spatial filtering, freshness and schedule calculations. Models interpret semantics without replacing unknowns with plausible details.

### Model integration and evidence limits

- Call at least one NVIDIA open-source model through Nebius Token Factory at runtime from the backend. Choose the eligible model, prompts, and structured output formats during implementation planning.
- Use the model for Observation extraction, category proposal, semantic Matching, evidence reconciliation, grounded Shared account synthesis and its Shared summary, discovery request interpretation and match explanation, impact assessment, and a separate Resolution assessment. The backend supplies actual candidate records and evidence, persists original contributions, and controls the records available to summarize.
- Do not attach a Report to an existing Happening automatically. Show one semantically ranked recommendation with its inspectable evidence and let the contributor confirm it or view alternatives. If the successful search finds no plausible candidate for a coherent occurrence, create a new Happening without an abstract newness question. If multiple candidates or continuity remain unclear, ask a focused ordinary-language clarification. Location, time, category, or a guessed cause alone never establishes identity; unknown causes stay unknown.
- Allow contributors to correct their own matching. Preserve association changes and recompute affected summaries and assessments against the corrected report sets.
- Let the LLM determine which supplied accounts enter a concise Shared summary without a required minority-inclusion count or majority threshold. Every underlying report remains inspectable. Link each important account or summary claim to its supporting Observations and original Reports, with the evidence’s time, scope, and provenance inspectable. Let summary selection remain concise, but do not discard relevant conflict or unknown scope from the underlying account. Generated text is not independent evidence.
- Version 1 evaluates contributor-submitted written accounts and metadata. Display source links as contributor-cited; do not automatically retrieve linked pages or claim that an unread link was checked. Discovery searches stored happenings rather than the web.

### Provisional resolution and chronology

- First report: immediately visible Reports received · 1 contributor. First Resolution report: immediately display Reports received with Resolution reported; awaiting more evidence, while leaving the assessment pending.
- Determine support using the same situation, full original extent, observation timing, source support, and remaining conflicts. There is no fixed report-count threshold, majority vote, truth score, or definitive verified Resolved state in Version 1.
- Treat earlier blockage and later reopening as possible change over time; recency alone is not proof. Different spatial scopes can support different states at the same time and do not alone establish conflict. Same-scope/same-period genuine conflicts remain visible with Reports received and unresolved uncertainty; preserve ambiguity when scope or timing is unknown. An undated report cannot override a dated observation solely through newer submission time.
- Represent partial improvement at the observed subject and spatial scope, such as one entrance open while the other remains blocked or unknown. Partial improvement does not establish full resolution. Ask one targeted follow-up if a resolution report lacks necessary extent information. Original extent can also require clarification; preserve it as unknown if not established. Display the submitted report while assessment remains pending.
- Automatically apply supported Reported resolved without human approval. Preserve each status change with its time, concise evidence explanation, and supporting report references in visible Status history. New evidence triggers reassessment and can withdraw the status.
- Treat freshness separately from resolution: No recent updates—current condition unknown does not claim either continued activity or resolution. Adjustable demo defaults are six hours after the latest relevant dated firsthand bridge observation and 24 hours after the latest relevant dated after-dark firsthand lamp observation. Daylight darkness alone does not establish an outage. Defaults for additional condition types remain implementation planning work.
- Scheduled activities enter Past activities after their scheduled end time. This does not establish that the activity occurred.

### Activities, discovery, and private updates

- Discover only existing stored Happenings, initially within visible bounds. Explain result relevance; offer Expand search area when there are no local matches. Selecting a result centers its map and opens its detail. Never invent activities to fill empty results.
- Provide working directions for any Happening and add-to-calendar for scheduled activities. Calendar and directions must be functioning actions rather than the prototype's stubs.
- Grant Activity organizer controls only through explicit I'm organizing this on new activity creation. Sharing another person's activity does not confer organizer control. Later claims on an existing community-shared activity are deferred.
- Activity observations about attendance, current conditions, a reported move, or wrapping up enter the same evidence/account workflow as other Happenings. Keep participant-observed state distinct from the organizer-provided plan; an observation must not silently rewrite that plan. Only the designated organizer controls schedule/location/cancellation. A participant's cancellation report is visible as Cancellation reported—awaiting organizer update alongside the existing schedule, without changing organizer-controlled cancellation solely from that report.
- Interested privately subscribes to organizer time/location/cancellation changes and is not an RSVP. Follow updates privately subscribes to disruption/safety provisional status transitions. Neither exposes public lists or counts.
- Notifications are in-app, available on return. Notify followers once for the first resolution report, again for supported Reported resolved, and with Resolution uncertain—new reports received plus evidence if that status is withdrawn. Additional raw reports alone do not each generate a notification.

## Out of Scope

- Social-feed primitives such as generic comments, likes/reactions, engagement ranking, gamification, generic local-news aggregation, unrelated chatbots, and reputation-based truth scores. Additional autonomous agents or model calls solely to make the architecture appear sophisticated are not requirements.
- A comprehensive new lifecycle taxonomy, unrestricted historical analytics, or a full event-sourcing architecture. V1 still requires a traceable evidence timeline and relevant account/status change history.
- External source searches, Check other sources, automatic linked-page retrieval/verification, authority/local-news validation, and background source checks; these are Round 2 work.
- Syndication detection across different cited sources, richer contributor/source identity signals, and wider-public moderation workflows. Bias-only hiding and the proposed Version 1 flag-and-hide flow are excluded.
- Statistical contributor-error estimation, noise weighting, popularity-based correctness scores, majority-vote resolution, and fixed corroboration thresholds. Statistical methods are deferred to an undecided later round.
- Definitive verified Resolved findings, continued-activity claims based on silence, or treating a model recommendation as independent evidence.
- Photo/video evidence uploads, RSVP/headcounts, public interest/follower lists or counts, push/email alerts, friends/social status displays, advanced calendar management, recurring activities, and richer attendance/organizer tools.
- Existing-activity organizer ownership claims; these require a later dedicated ownership-check process.
- Native phone clients, blockchain/federation, and web discovery that invents or fetches happenings outside the stored app data.
- Remaining setup choices: app/worker hosting, service credentials, the exact eligible Nemotron model identifier after the integration check, API and model-output contracts, and freshness defaults beyond the selected demo conditions. The framework, database, auth provider/sign-in method and map stack are confirmed above.
