# Report submission — ticket #4

Source: [ticket #4](https://github.com/Pcworker996/nebius-hack/issues/4), with the browser/real HTTP API/PostgreSQL testing boundary in ADR 0003 and the contributor-confirmed matching boundary in [ADR 0004](adr/0004-confirm-matches-before-membership.md).

The October 19, 2026 revision records the product owner's accepted progressive candidate-review flow. This local implementation removes the `clearlyNew` choice and adds bounded nearby retrieval, evidence-backed semantic recommendations, explicit confirmation, automatic first-Happening creation only after a successful no-match decision, and retryable processing. Local verification passed: TypeScript, the full mobile/desktop browser suite (40/40), and the production build. The suite used controlled external auth/model HTTP fixtures and a fresh disposable local PostgreSQL database; it does not establish live-provider success.

Ticket #4 remains open for live Google/Supabase Auth and Nebius verification, exact Nemotron model selection, and the explicitly unresolved separate-occurrence clarification flow. The matching migrations in this change have only been exercised against a disposable local PostgreSQL test database; hosted schema state and Vercel's database target are not verified here. When the model cannot treat one Report as one coherent occurrence, the Report remains unassigned; the implementation does not collect a separate-occurrence clarification answer or distribute one Report across Happenings. Do not treat local controlled-service success as live provider verification.

## Agreed behavior and responsibilities

- Public browsing remains available. Contribution uses Google-only Supabase PKCE sign-in, verified by the server with `getUser`. The browser retains its draft through sign-in. A person chooses a public display name; email and Google profile names are never copied into public evidence.
- The form collects original words, an adjustable pin (latitude/longitude), location description, explicit observation time or unknown, provenance, and an optional contributor-cited HTTP(S) source URL. It does not ask for a category or whether the situation is "completely new." An existing detail and prefilled location are search context, not proof of membership.
- `POST /api/reports` saves the immutable original before processing. A client-generated UUID is an idempotency key bound to the verified contributor; replay with changed content is rejected. `GET /api/reports/:id` exposes only that contributor's saved submission and processing state. Public views expose only appropriate Report metadata, never auth data.
- Candidate retrieval is deterministic server work. The implementation defaults to a 1,500 m radius and a symmetric 30-day window around a known observation time. If the incoming observation time is unknown, do not apply a time cutoff; stored observations with unknown times remain eligible in a bounded search. Search spatially against Happening and associated Report coordinates, and rank by stored Observation chronology and spatial distance. Return at most five Happenings, each with up to three relevant original Report/Observation records; pass spatial-scope text in that evidence packet for semantic comparison rather than treating it as a hard geospatial filter. A Happening without linked Observation evidence is not a candidate. Order a selected-detail hint first, then temporal proximity, spatial distance, and stable ID. These are explicit implementation defaults for review, not independently validated product constants. Category can inform semantic ranking but is not a hard identity filter.
- The backend sends the saved Report's original words, observation time, contributor-described location and pin coordinates, provenance and cited URL alongside a bounded, inspectable packet of candidate evidence to the model for semantic ranking. Candidate evidence includes relevant existing Reports/Observations and their times, locations, scopes, and provenance; a generated Shared summary alone is not sufficient. The model returns only one of the supplied candidate IDs with evidence references, `no_plausible_match`, or `uncertain`. Software validates all IDs and references; the model cannot create a candidate or write membership directly.
- Use progressive review in the UI. Show the model's best suggested Happening first with its location, distance, chronology, and cited original evidence. The contributor can use that Happening, say the displayed candidates describe a different situation, or open up to four more nearby candidates. Do not ask the contributor to classify the Report as new. A confirmed candidate choice is a separate, attributed matching decision; it does not edit the original Report.
- If a successful search and semantic comparison find no plausible candidate, a coherent single-occurrence Report creates a new Happening. If the model finds a likely candidate, membership is committed only after the contributor confirms it. If candidate identity remains ambiguous, keep the Report unassigned and show a focused question with nearby evidence; the contributor can confirm a candidate, say none fit, or leave it unassigned while unsure. This slice does not collect free-form clarification text. The separate-occurrence case remains a proposed, unconfirmed flow below; do not distribute one Report across multiple Happenings automatically.
- Persist the ordered candidate IDs and evidence snapshot, model recommendation, and final matching outcome in the Report's `nearhood.report_processing` row. Store the candidate IDs the contributor says were shown separately from the immutable Report. The outcome is either `matched` with the selected Happening ID or `create_new`; record whether `create_new` followed a successful semantic no-match or the contributor's rejection of shown candidates, and record actor/time for a user choice. A durable `match_review` state lets the contributor resume after reload. The server revalidates that a selected Happening still exists and was in the persisted candidate set before committing.
- Processing remains a separate authorized server operation. A bounded lease and attempt token permit retry after interruption and reject obsolete completion. Model, database, or candidate-search failures leave the saved Report intact and retryable; a failed or incomplete search is never interpreted as "no match." Match confirmation or new-Happening publication occurs in a short transaction. Existing Happenings and accounts are unchanged until a match is confirmed.
- The backend calls Nebius Token Factory for structured extraction and initial evidence-linked claims. The exact Nemotron identifier remains unset until a live structured-output/evidence/latency check succeeds. Software assigns IDs, timestamps, memberships and references and attaches the original text to its Observations and initial claim. Source links remain contributor-cited and are never fetched.

## Lifecycle and outcomes

1. `saved` → `processing`: persist the original Report, contributor, idempotency key, location, time and provenance before any model request.
2. `processing` → `match_review`: candidate search and model comparison succeed and produce a reviewable candidate recommendation.
3. `match_review` → `published`: the contributor confirms a supplied candidate; attach the Report's Observations and publish the resulting provisional account update atomically.
4. `processing` → `published`: a successful search finds no plausible candidate and the Report describes one coherent occurrence; create a new Happening and its first account atomically.
5. `processing` or `match_review` → `clarification`: evidence cannot distinguish candidate Happenings. Keep it unassigned and show a focused question and evidence-backed choices. The contributor may select a candidate, indicate none of the shown Happenings fit, or leave it unassigned while unsure. The separate-occurrence case remains pending product confirmation.
6. Any processing/search/provider failure → `pending`: preserve the Report and offer retry of that same Report. Invalid or obsolete match choices are rejected and the candidates are refreshed.

`GET /api/reports/:id` returns the owner's saved Report and matching state. An owner-authorized `POST /api/reports/:id/match` confirms either a supplied candidate ID or that the shown candidates describe a different situation. The endpoint is idempotent for the same choice, rejects IDs outside the persisted candidate set, and records the contributor's choice without changing the original Report. A repeated conflicting choice after publication is reserved for the later correction flow in #6.

## Decision awaiting product confirmation

For a Report whose text describes separate occurrences, preserve one original Report and do not force unrelated Observations into one Happening. The proposed path is to retain any derived interpretations as unassigned and ask a focused clarification; clarification answers, if confirmed, will be separate attributed and timestamped records, never edits to the original text. Automatic distribution of one Report across multiple Happenings remains excluded. The user has not yet confirmed this separate-occurrence behavior, so it must not be presented as agreed or implemented.

Ticket #4 covers matching the initial submitted Report to a nearby existing Happening or creating the first Happening. Ticket #5 covers a later Report that updates an existing Happening; its automatic-attachment policy should be reconciled with this candidate-review interaction before #5 implementation.

## Acceptance and failure checks

- The contribution form and request contract contain no `clearlyNew`/newness question. Save and reload a Report without asking the contributor to understand Happening identity.
- Search a bounded, location/time-relevant candidate set of up to five evidence-bearing Happenings. Verify the 1,500 m/30-day defaults, unknown-time handling, hint ordering, and no hard category filter. A selected detail is a candidate, not membership.
- Show a single best recommendation first, expose supporting original evidence and chronology, and make other nearby candidates available on request. Confirming a candidate attaches the Report once and preserves previous evidence/account history. Saying the shown candidates describe a different situation results in a new Happening only after a successful search and a coherent Report.
- A successful search with no plausible candidates creates a first Happening. Ambiguous candidates or unclear continuity remain unassigned for clarification. The separate-occurrence flow is still pending product confirmation. Search/database/model failure remains retryable and never creates a new Happening by default.
- Reject candidate IDs and evidence references not supplied by the server. A stale candidate choice is rejected and refreshed. A retry or concurrent confirmation cannot duplicate a Report, Happening, membership, or account publication.
- Cover candidate ranking with reports at nearby and separated locations, overlapping and unknown observation times, same-category separate occurrences, a partial change within a larger Happening, an empty successful search, a search failure, and contributor rejection of the suggested candidate through the browser/API/database boundary.
- Retain existing checks for Google draft preservation, chosen public name/private email, unauthorized requests, unknown times, source-based reports, multiple scoped claims, failed-processing reload/retry, candidate isolation, invalid references, long Reports, and duplicate/concurrent submissions. Live provider verification complements controlled external-service tests; missing credentials leave it incomplete.

## Setup and verification

1. Apply the ordered SQL files in `db/migrations/` to a disposable local test database with `npm run db:setup -- --seed`. Browser tests use `TEST_DATABASE_URL` or the documented local `nearhood_test` database. Never point setup or tests at production user data. Hosted matching migrations and Vercel configuration are not verified by this local check.
2. Set `APP_ORIGIN`, `SUPABASE_URL`, and `SUPABASE_PUBLISHABLE_KEY` (see `.env.example`). Enable only Google as a sign-in provider and allow the exact `/auth/callback` redirect in Supabase and Google's corresponding Supabase callback in Google Cloud. Provider credentials stay in Supabase.
3. Set `NEBIUS_API_KEY`; run `npm run model:check`. It discovers available exact NVIDIA Nemotron identifiers and checks structured extraction, grounded references, multiple scoped claims, unknown/source-based information, separate occurrences, and latency. Inspect `.local/report-model-check.json` and set `NEBIUS_MODEL` to the selected passing identifier. There is deliberately no unverified model default.
4. Run the typecheck, browser/API/database journeys, full suite, and production build after implementation. Tests control external auth/model HTTP services while retaining real application routes and isolated local PostgreSQL persistence. Fixtures must not authorize production requests or introduce an application auth bypass.
5. Walk through real Google sign-in, candidate review and a live model-backed submission before declaring ticket #4 complete. Controlled-service success does not prove Google dashboard setup, hosted migrations, or runtime model eligibility/quality.

The Supabase security advisor cannot run against a standalone PostgreSQL installation because it lacks Supabase's `anon`/`authenticated` roles and internal schemas. Direct catalog checks verify RLS and private-schema boundaries. The migration ledger enables RLS and revokes Data API grants when those roles exist.
